**v5 — migrated to the Tauri (Rust) + React stack (ADR-013).** Earlier versions of this file described FastAPI/uvicorn tasks, and before that Xcode/SwiftUI/Swift-concurrency tasks, that no longer apply — see `docs/DECISIONS.md` for why the stack changed each time. ## Phase 0.3 — Traffic Observation Backend

*Hardest phase. Don't start until 0.1–0.2 are solid and reliable.*

- [x] Spike: confirm `mitmproxy --mode local:<pid>` works standalone against a process you control, before wiring anything into the app. Done 2026-09-07: full HTTP and HTTPS capture confirmed against `test-target/network_test_target.py` (both roles — a controlled process making real requests, mitmproxy attached via `--mode local:<pid>`), including a large (512 KiB) response, a slow response, and a request carrying fake sensitive-looking fields (password/token/Authorization/cookie) all correctly captured. No `sudo` needed at any point. Full method, the three one-time manual-approval steps required (system extension, VPN configuration, CA trust — none scriptable), and a significant new finding (loopback/127.0.0.1 traffic is not observable at all by this capture mode) are recorded in `docs/PERMISSIONS_AND_PLATFORM.md`'s "Traffic capture" section. `test-target/network_test_target.py` (the `NetworkTestTarget` script this spike needed and the Cross-cutting section had never built yet) was updated to target the machine's real interface IP instead of loopback because of that finding, keeping one `local_connection` scenario on loopback deliberately to demonstrate the limitation rather than quietly avoid it.
- [x] Design the core-to-helper boundary: how the Rust core launches/manages the `mitmdump`-based helper process (`std::process::Command`/`tokio::process`), and the IPC format (local socket + JSON via `serde`) between them. Done 2026-09-07: `src-tauri/src/providers/traffic.rs`. The core binds a `tokio::net::UnixListener` at a session-scoped temp path *before* spawning `mitmdump`, so there's no race for the addon to connect into; the addon (`src-tauri/resources/mitm_addon.py`) connects once and streams one newline-delimited JSON object per captured flow. One-directional by construction (addon → core only) — the core never sends anything back that could influence what the addon does to a flow, which is what actually enforces "no `intercept()`/`set()`/replay" below, not just a comment saying so.
- [x] Write the mitmproxy addon script: consume `request`/`response` events only — no `intercept()`, no `set()`, no replay hooks, by construction. Done: `src-tauri/resources/mitm_addon.py` implements only `response(flow)`/`error(flow)`; it never touches `flow.request`/`flow.response` in a way that changes what's sent or received.
- [x] Implement `TrafficProvider` trait + mitmproxy-backed implementation. Done: `MitmproxyTrafficProvider` (`src-tauri/src/providers/traffic.rs`) — `start(pid)`/`stop()`/`take_flows()`, synchronous kickoff spawning the subprocess + a reader task internally (matches `ProcessProvider`'s `&self`-not-`&mut self` shape). **Deliberately does not pass `--ssl-insecure`** — see that decision's reasoning in the module doc comment: this is a passive observation tool, and silently disabling upstream TLS verification would hide a real MITM attack on the very traffic being observed, in exchange for convenience testing against one script's self-signed cert.
- [x] Write the mitmproxy addon so it applies tier-1 (highly-sensitive) redaction before emitting anything over the helper→core IPC socket, per the shared field-name list in `docs/PRIVACY_AND_SECURITY.md`'s "Starter sensitive-field list" — the IPC schema must have no field capable of carrying an unredacted tier-1 value (`docs/PRIVACY_AND_SECURITY.md`'s "two redaction checkpoints"). **Implemented but not verified by anything that runs again — flagging that here rather than leaving this checkbox overclaiming.** `src-tauri/resources/tier1_redaction_fields.json` is the single shared field list (read by the addon now; the Rust core's Phase 0.4 Redactor reads the same file, not a copy). Covers headers, JSON bodies (recursive, nested), form-urlencoded bodies, and query strings. Known, documented limitation: binary/unstructured bodies aren't redaction-checked — flagged explicitly in the addon's own doc comment rather than silently assumed covered. The "covers X/Y/Z" claim above was only ever checked by hand via ad-hoc `python3 -c "..."` calls during implementation, which don't exist anywhere in the repo now — no unit test and no Rust integration test exercises `sensitive_fields`/redaction at all (confirmed by grep). Logged and tracked as **Phase 0.3 code-review gap 1/6** below, the single highest-priority item in that list precisely because this checkbox is the safety-critical one.
- [x] Add `ObservationCapabilities` **per provider** (not per connection) as an Engine-aggregated struct, per `docs/DATA_MODEL.md`, reported by a `get_capabilities()` command — per-connection variability stays in `ObservationStatus`, don't add a capability field to `NetworkConnection`. (Moved here from an earlier Phase 0.2 placement to match `ARCHITECTURE.md` and `DATA_MODEL.md`, both of which already said Phase 0.3.) Done: `src-tauri/src/models/capabilities.rs`, `ObservationEngine::get_capabilities`, `commands::get_capabilities`. Each of the four providers only sets the fields it owns; the Engine reads exactly those out rather than attempting a generic merge.
- [x] Define `TrafficProvider` capability reporting (`process`, `http_metadata`, `https_metadata`, `request_body`, `response_body`, ... — the `ObservationCapabilities` fields in `docs/DATA_MODEL.md`, not a separately-invented name set) — distinguish "provider unavailable" from "this traffic type is unsupported". Done: `TrafficProvider::capabilities()` default impl reports `http_metadata`/`https_metadata`/`request_body`/`response_body` as `available`, `raw_packet_data` as `unavailable` (mitmproxy-based, not packet capture — the documented Phase 0–1 ceiling, `docs/DATA_MODEL.md`).

## Definition of done for the whole project

Select a running process and obtain Levels 1–3 (process, network, protocol) wherever those observations are technically and legitimately available, with the UI explicitly distinguishing **observed**, **denied**, **unsupported**, and **stale** information rather than presenting any of them as empty or current. Level 4 (HTTP/application payload) is available only where technically and legitimately observable, degrading to the same explicit categories rather than silence. Highly-sensitive data is never captured in raw form at all; potentially-sensitive data is redacted by default and irreversibly before it ever reaches storage or export. Nothing in the app is capable of modifying, replaying, or injecting traffic.
