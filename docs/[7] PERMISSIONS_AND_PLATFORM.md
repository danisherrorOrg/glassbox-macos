# Permissions & Platform — Process Network Inspector

This document exists to separate what's actually been tested from what's assumed. Every claim below is tagged **VERIFIED**, **ASSUMED**, or **DECISION** — update tags as the Phase 0 spike (`TODO.md`) produces real findings. Nothing in this file should be treated as fact until it carries a VERIFIED tag from an actual test on this machine.

## Framing: two different problems, not one

**Process and socket inspection** (`ProcessProvider`/`SocketProvider`) and **traffic capture** (`TrafficProvider`) have entirely different permission stories. Conflating them (as an earlier draft of the project report briefly did) overstates the cost of Phases 1–2 and understates why Phase 3 is genuinely harder.

## Process and socket inspection

- **VERIFIED (2026-09-07, Phase 0 spike):** A Rust process run as your own user can enumerate its own and other same-user processes' basic info via `sysinfo`/`netstat2` (or direct `libproc` FFI where those crates don't cover a need), without needing elevated privileges — the same OS-level visibility a compiled binary run from Terminal has always had, independent of language. Confirmed: `sysinfo` saw 666 processes and `netstat2::get_sockets_info()` returned every one of this machine's ~30 live TCP/UDP sockets, correctly attributed to their owning same-user PID, with no privilege beyond the ordinary user account running the probe. See the checklist below for the full detail.
- **VERIFIED (2026-09-07, Phase 0 spike):** Enumerating sockets belonging to *other users'* processes needs root, same as it would from a Terminal session (`sudo lsof` today; the equivalent underlying `libproc` call requires the same privilege regardless of what calls it). Confirmed two ways: (1) unprivileged `lsof -i -P -n` on this machine returned zero sockets outside the current user, even though root-owned daemons with sockets (`mDNSResponder`, mDNS/UDP, etc.) were running; (2) direct `libproc` FFI (`proc_pidinfo(PROC_PIDLISTFDS, ...)`, the exact call `netstat2` uses internally on macOS) against 8 distinct other-user daemons (uids 0, 65, 88, 202 — `launchd`, `logd`, `configd`, `syslogd`, `WindowServer`, `mDNSResponder`, `coreaudiod`, `mDNSResponderHelper`) failed uniformly with `errno=1` (`EPERM`, "Operation not permitted"). See checklist item 2 below for why this exact refusal shape matters for `permission_denied` mapping.
- **ASSUMED:** Because this ships as a code-signed native app rather than a sandboxed Mac App Store app, Apple's app-sandbox entitlement restrictions don't apply — an unprivileged, non-sandboxed process has the same OS-level visibility as any other unprivileged process you run. (If Mac App Store distribution is ever pursued later, this assumption must be re-verified against the sandbox's actual entitlement restrictions — see "Running the app itself" below.)
- **ASSUMED — unaffected by this spike:** The process/socket visibility measured by the Phase 0 spike (below) is identical under the hardened runtime in a signed, notarized build as it is under `cargo tauri dev` — no TCC (Transparency, Consent, and Control) prompt or additional entitlement is required for `libproc`/`sysinfo` reads of same-user processes, including reading another same-user process's `executable_path`. **This spike does not verify this claim** — the probe was a bare `cargo build` binary run from a terminal, not even `cargo tauri dev`, let alone a signed/notarized/hardened-runtime build (deliberately, per `TODO.md` step F: "doesn't need the real project scaffold yet"). **TO VERIFY:** re-run the spike's checklist once against a `cargo tauri build` signed binary, not only a dev build — a dev-build spike passing is not sufficient evidence this assumption holds, since TCC prompts and hardened-runtime entitlement checks can differ between the two. If this assumption turns out false, it surfaces at Phase 1.0's code-signing step (`TODO.md`) unless caught here first.

### Implementation guidance for `SocketProvider`/`ProcessProvider` (Phase 0.1) — surfaced by the spike, not previously documented

- **`netstat2` cannot be the source of `permission_denied` for a targeted-PID call.** Reading its macOS backend source (`integrations/osx/netstat.rs`, `iterate_netstat_info`): for each PID it calls `list_all_fds_for_pid`, and on any error — including `EPERM` on another user's process — it does `continue` and moves to the next PID, discarding the error entirely. A cross-user PID is therefore indistinguishable, from `get_sockets_info()`'s return value alone, from a same-user PID that simply has zero open sockets. `docs/OBSERVATION_CONTRACT.md`'s `permission_denied` status ("`lsof` couldn't see another user's process without elevation") is a real, correct status to model — but `SocketProvider` must derive it itself (compare the target PID's owning uid against the current process's own uid *before* calling into `netstat2`, and set `permission_denied` proactively) rather than expecting a signal back from the crate. This affects `get_connections(pid)`'s outer call-level status specifically (`OBSERVATION_CONTRACT.md`'s two-level-status note).
- **`sysinfo::Process::user_id()` is not reliable enough to drive that same-uid comparison.** In this spike, `sysinfo` 0.39.6 returned `uid=0` for PID 170 (this machine's per-user `loginwindow` process), when the process's actual owning uid — confirmed via `ps -p 170 -o uid` — is the logged-in user's own uid (`501`), not root. Separately, `sysinfo` returned no uid at all (`user_id() == None`) for 268 of 666 visible processes on this run. A `SocketProvider`/`ProcessProvider` uid comparison should go through `libproc` directly (e.g. `proc_pidinfo(PROC_PIDTBSDINFO)`'s `pbi_uid` field, the same source `ps`/`lsof` themselves use) rather than trusting `sysinfo`'s uid for this specific same-user-vs-other-user decision — `sysinfo` remains fine for the other `ProcessObservation` fields it's already scoped for (name, cpu, memory).
- **Different `libproc` calls have different privilege boundaries — "libproc" is not one uniform permission bucket.** `proc_pidpath()` (executable path lookup) succeeded, unprivileged, against every other-user process tried in this spike, including `pid 1`/`launchd` (root) — a strictly *more* permissive result than the FD-listing calls above, and more permissive than the existing ASSUMED claim above scoped for ("another same-user process's `executable_path`") actually requires. Don't generalize a privilege result from one `libproc` call (e.g. `PROC_PIDLISTFDS`) to another (e.g. `proc_pidpath`) without checking each independently — this spike only checked the two calls named here.

## Traffic capture

- **VERIFIED (2026-09-07, Phase 0.3 spike):** mitmproxy's `--mode local:<pid>` capture needs **no `sudo`/root at all** on this machine (macOS 26, Apple Silicon) — every command in this spike ran as the ordinary logged-in user. What it does need, confirmed empirically, is **three separate one-time manual approvals**, none of which can be scripted or automated (each is a macOS security boundary deliberately requiring human interaction — confirmed by directly attempting to automate all three, all of which either hung indefinitely or produced a clearly-labeled permission error until a human clicked through the corresponding system UI):
  1. **System Extension approval** — the first `mitmdump --mode local:<pid>` run installs and activates `org.mitmproxy.macos-redirector.network-extension`, which sits at `[activated waiting for user]` (`systemextensionsctl list`) until approved in System Settings → General → Login Items & Extensions → Network Extensions. Until approved, the redirector helper app starts but nothing happens (no error, no capture, no log output) — easy to mistake for "not implemented yet" rather than "waiting on approval."
  2. **VPN/network-configuration approval** — a *separate* macOS system dialog, distinct from step 1, appears the first time `mitmdump` actually tries to activate the redirect (not when the extension is installed). Denying or missing it produces a specific, identifiable error: `Error Domain=NEVPNErrorDomain Code=5 "permission denied"`, and the redirector exits immediately (`mitmproxy/mitmproxy#7419` on GitHub is the same failure, same root cause: the dialog was missed, not a bug). This dialog did **not** appear when `mitmdump` was launched as a background/non-interactive process — it only appeared, and only became clickable, when run from a real interactive terminal session. A background-launched attempt just hangs with no output and no visible prompt.
  3. **CA certificate trust** — as already assumed, but confirmed to specifically need a Keychain *authorization* dialog (Touch ID/password), not just a file operation: `security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db ~/.mitmproxy/mitmproxy-ca-cert.pem` blocks on a `SecurityAgent` prompt (visible via `ps aux | grep SecurityAgent` while pending) until a human approves it — a script running this non-interactively hangs the same way step 2 does. **User-level (login keychain) trust was sufficient** — no admin/system-keychain trust (which would need `sudo`) was required to get `curl`/mitmproxy's own TLS stack to accept the cert.
  All three are **one-time**: once granted, subsequent `mitmdump` runs (including targeting different PIDs) work without re-prompting. None of the three steps above needs repeating per-target-process or per-session.
- **VERIFIED (2026-09-07, Phase 0.3 spike) — a new, previously-undocumented finding, not something this section originally asked to check:** **loopback (127.0.0.1) traffic is not observable at all** by `mitmproxy --mode local:<pid>`, regardless of the three approvals above. Confirmed directly: identical HTTP/HTTPS requests from the same test process were captured immediately and completely when the destination was the machine's real network-interface IP, and produced zero captured flows — no `client connect` line, nothing — over 12+ seconds of active traffic when the destination was `127.0.0.1`, even to the exact same server process on the exact same machine. This matches Apple's own documented `NetworkExtension` framework behavior (the redirector's underlying mechanism — see the `DECISION` below): the framework's content-filtering/transparent-proxy providers do not see traffic that both originates and terminates on the loopback interface. **Downstream consequence:** any process being observed whose traffic is (partly or entirely) to `127.0.0.1` — common for apps talking to a local backend, dev servers, Electron apps, etc. — will show that traffic's sockets fine via `SocketProvider` (Levels 1–3 unaffected) but will get `unsupported` at the HTTP/HTTPS layer (Level 4) for connections to loopback destinations specifically, the same category as a pinned-cert or QUIC connection, not a bug to fix later. Phase 0.3's `TrafficProvider` implementation must treat a loopback `remote_addr` as a known-`unsupported` case up front, not something to debug when capture "doesn't work" for an otherwise-correctly-configured session. `test-target/network_test_target.py`'s scenarios were updated to target the machine's real interface IP (not `127.0.0.1`) specifically because of this finding — see that script's module docstring for the full reasoning and its dedicated `local_connection` scenario, which deliberately still uses loopback to keep this limitation demonstrable/testable rather than silently avoided.
- **DECISION:** A Network Extension–based `TrafficProvider` is still not achievable as a pure Rust/Tauri component — `NetworkExtension.framework` entitlements require a Swift/ObjC system-extension target that subclasses Apple's own framework classes; that requirement doesn't go away just because the host app is now native. What changes under `DECISIONS.md` ADR-013 is that this extension target can be embedded inside this app's own signed `.app` bundle using Apple's normal system-extension tooling, rather than needing an entirely separate distribution mechanism the way it would have under the FastAPI-era stack. This is not a permanent dead end for the project, but it remains a real, separate piece of Swift/ObjC work with its own entitlement-request lead time. If deeper packet-level capture is ever needed beyond what mitmproxy's local mode offers, that embedded-extension path or accepting the mitmproxy-based approach as this project's practical ceiling are the two realistic choices. See `DECISIONS.md`. (The Phase 0.3 spike confirmed this concretely, not just by reasoning about entitlements in the abstract: mitmproxy's own `local:<pid>` implementation *is* a `NetworkExtension`-based system extension under the hood — `org.mitmproxy.macos-redirector.network-extension` — which is exactly why it needs the system-extension and VPN-configuration approvals above. This project inherits that same mechanism and its same one-time approval requirements by depending on mitmproxy, rather than needing to build and get its own separate extension approved.)
- **ASSUMED:** Certificate pinning will still defeat this approach on some target processes exactly as it would for any MITM-based approach, regardless of stack — this isn't a platform-permission problem, it's inherent to how the target app is written, and is a legitimate stopping point per the original learning path this project is based on. **Switching stacks does not change this risk at all** — it's identical to what ADR-009 already documented.

## Running the app itself

- **DECISION:** This ships as a single native, code-signed, notarized `.app`, built via `tauri build` — a real distribution path this project didn't have under the FastAPI-era stack (`DECISIONS.md` ADR-013), and closer to what the original Swift/SwiftUI plan (ADR-008) would have provided. Mac App Store distribution remains a separate, explicit future decision — it requires opting into App Sandbox entitlements, which would need re-verifying every assumption above about unsandboxed process/socket visibility; a signed-but-not-sandboxed direct download is the default target for this project, not App Store review.
- **ASSUMED:** An Apple Developer Program membership is available (or will be obtained) before Phase 1.0 — code signing and notarization both require one. Notarization also has a real turnaround time, independent of anything this project controls. An unavailable membership defers packaging (Phase 1.0's signing step) without blocking any earlier phase — nothing before Phase 1.0 depends on being signed.
- **DECISION:** Because there's no App Sandbox constraining this build, the OS-level privilege boundary around process/socket enumeration (same-user vs. other-users') is the thing that matters most for what Phase 0.1 can see without elevation — see the assumptions above.
- **DECISION:** For the "other users' processes" and any other privilege-elevation need, prefer macOS's Service Management framework (`SMAppService`, or the older `SMJobBless`) to install a small, signed, privileged helper tool with a real authorization prompt, over asking the user to launch the whole app with `sudo`. This is a genuine improvement available to a signed native app that a bare interpreted script never had a clean equivalent for. Not required for Phase 0.1 (same-user visibility needs no elevation) — worth designing once cross-user visibility is actually prioritized.

## First technical spike (rescoped by the pre-implementation Round 2 audit — see `DECISIONS.md` ADR-014) — **run 2026-09-07, results below**

This determines whether Phase 0.1 is trivial or the project's first real blocker — same spike as originally planned, scoped to Rust's system-call boundary (`sysinfo`/`netstat2`/`libproc`). An earlier version of this section asked only the privilege question below (question 1–2). That's necessary but not sufficient: Phase 0.1's actual type design (`DATA_MODEL.md`'s `SocketObservation`) also depends on three data-shape questions (3–5) that a privilege-only spike wouldn't answer, and a spike that clears privilege while leaving those open would return a false green light.

**Method:** a throwaway Rust binary (`cargo init`, not part of the real project scaffold, not committed to this repo per `TODO.md` step F's own framing) depending on `sysinfo = "0.39"`, `netstat2 = "0.11"`, and `libc`, run unprivileged (uid 501) on this machine (macOS 26 / Darwin 25.6.0, Apple Silicon). Cross-checked against unprivileged `lsof -i -P -n` and `netstat -an` run directly in the terminal. Toolchain installed via `brew install rust` (`rustc`/`cargo` 1.98.0) for this spike — none was present before.

1. **Same-user visibility:** ✅ **Yes, confirmed, no elevation needed.** `sysinfo::System::refresh_all()` enumerated 666 processes; `netstat2::get_sockets_info()` returned every live TCP/UDP socket on the machine (~30 at time of test), all correctly attributed to same-user PIDs, all matching what unprivileged `netstat -an`/`lsof -i -P -n` independently showed.
2. **Other-users' visibility:** ✅ **Confirmed needs root; exact refusal shape recorded.** Unprivileged `lsof -i -P -n` returned zero cross-user sockets (only `danishmahajan`-owned rows), even though root-owned daemons with open sockets were running. At the `libproc` FFI layer — the exact call `netstat2` uses internally on macOS (`proc_pidinfo(PROC_PIDLISTFDS, ...)`) — the refusal is a **hard, uniform denial**: return value `0`, `errno = 1` (`EPERM`, "Operation not permitted"). Verified against 8 other-user daemons spanning 4 different uids (0, 65, 88, 202): `launchd`, `logd`, `configd`, `syslogd`, `WindowServer`, `mDNSResponder`, `coreaudiod`, `mDNSResponderHelper` — all failed identically. It is **not** an empty result and **not** partial data — it's an explicit denial with a stable errno, but (per the implementation-guidance note above) `netstat2`'s own Rust API silently swallows that errno rather than surfacing it, so `SocketProvider` must detect the cross-user case itself rather than rely on an error coming back from the crate.
3. **PID attribution:** ✅ **Yes, `netstat2` attributes every socket to a PID on this machine, no `libproc`-FFI-from-the-start fallback needed.** All ~30 sockets returned by `get_sockets_info()` carried a non-empty `associated_pids`; zero returned with an empty PID list. (`netstat2`'s macOS backend is itself a thin wrapper over `libproc`'s `PROC_PIDLISTFDS`/`PROC_PIDFDSOCKETINFO` — confirmed by reading its vendored source — so this also answers "does `netstat2` actually reach `libproc` correctly on this OS version," not just "does the crate's public API look right.")
4. **Byte counters:** ❌ **Negative — neither `bytes_sent` nor `bytes_received` is obtainable from any candidate source.** Confirmed structurally, not just by an empty sample: `netstat2::TcpSocketInfo`/`UdpSocketInfo` (`src/types/socket_info.rs`) have no byte-count fields at all, and the raw macOS kernel structs those types are built from — `in_sockinfo`/`tcp_sockinfo` in `libproc.h`, inspected directly via the crate's own `bindgen` output against `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/libproc.h` — carry no byte-counter fields either. This is a platform-API gap, not a crate-choice or implementation-effort gap: no amount of extra `libproc` FFI work recovers this data, because the kernel-exposed struct simply doesn't track it. **Per the contingency below, the report's Level-3 promise has been amended** (`docs/process-network-inspector-report.md`, "Four levels of visibility") — `bytes_sent`/`bytes_received` stay in `SocketObservation` as `Option<u64>` (already correctly optional) but render as "not reported" for every macOS connection via this provider stack, permanently, not just for some.
5. **Socket state:** ✅ **Yes, obtainable, and the vocabulary lines up with `lsof`'s.** `netstat2::TcpState` enumerates the full BSD TCP state machine (`Closed`, `Listen`, `SynSent`, `SynReceived`, `Established`, `CloseWait`, `FinWait1`, `Closing`, `LastAck`, `FinWait2`, `TimeWait`) — the same state set `lsof`/`netstat` report, just Rust-`PascalCase` instead of `lsof`'s upper-case (`Established` vs. `ESTABLISHED`), a display-formatting detail for `SocketProvider` to handle, not a missing-data one. Live-observed on this machine: `Established`, `Listen`, `Closed` (the states actually in use at test time — the full 11-state enum is defined structurally regardless of which states happened to be live).

**Contingency, applied:** questions 1, 2, 3, and 5 came back positive — same-user visibility needs no elevation, so the `SMAppService` privileged-helper design stays "worth designing once cross-user visibility is prioritized," **not** promoted to a Phase 0.1 prerequisite, and `netstat2` is confirmed sufficient for `SocketProvider` (no `libproc`-FFI-from-day-one requirement). Question 4 came back negative, exactly the "if (4) fails" branch this section already anticipated: `bytes_sent`/`bytes_received` render as "not reported" (per the field-level-absence rule in `OBSERVATION_CONTRACT.md`) and the report's Level-3 wording has been corrected accordingly (see above) rather than silently shipping unpopulated fields. See `pre-implementation/[2] FINDINGS.md` (`PIF-045`, `PIF-046`) for the traceable finding/decision record, and `pre-implementation/[3] TODO.md` step F for the checklist this closes out.
