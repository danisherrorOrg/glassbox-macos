# Permissions & Platform — Process Network Inspector

This document exists to separate what's actually been tested from what's assumed. Every claim below is tagged **VERIFIED**, **ASSUMED**, or **DECISION** — update tags as the Phase 0 spike (`TODO.md`) produces real findings. Nothing in this file should be treated as fact until it carries a VERIFIED tag from an actual test on this machine.

## Framing: two different problems, not one

**Process and socket inspection** (`ProcessProvider`/`SocketProvider`) and **traffic capture** (`TrafficProvider`) have entirely different permission stories. Conflating them (as an earlier draft of the project report briefly did) overstates the cost of Phases 1–2 and understates why Phase 3 is genuinely harder.

## Process and socket inspection

- **ASSUMED:** A Rust process run as your own user can enumerate its own and other same-user processes' basic info via `sysinfo`/`netstat2` (or direct `libproc` FFI where those crates don't cover a need), without needing elevated privileges — the same OS-level visibility a compiled binary run from Terminal has always had, independent of language.
- **ASSUMED:** Enumerating sockets belonging to *other users'* processes needs root, same as it would from a Terminal session (`sudo lsof` today; the equivalent underlying `libproc` call requires the same privilege regardless of what calls it).
- **ASSUMED:** Because this ships as a code-signed native app rather than a sandboxed Mac App Store app, Apple's app-sandbox entitlement restrictions don't apply — an unprivileged, non-sandboxed process has the same OS-level visibility as any other unprivileged process you run. (If Mac App Store distribution is ever pursued later, this assumption must be re-verified against the sandbox's actual entitlement restrictions — see "Running the app itself" below.)
- **TO VERIFY (Phase 0 spike):** whether `sysinfo`/`netstat2` on this machine can read connection info for other users' processes without elevated privilege, and exactly what the underlying `libproc` calls refuse without it.

## Traffic capture

- **ASSUMED:** mitmproxy's `--mode local:<pid>` capture requires accepting its CA certificate into your trust store once, and needs to run with enough privilege to redirect that specific process's traffic — verify exactly what privilege level this needs on your machine (some local-capture modes need `sudo`, some don't, depending on the macOS version and mitmproxy's implementation). This is unchanged by the move to Rust/Tauri: the helper is still Python, still spawned and managed as a subprocess (`ARCHITECTURE.md`), and its privilege requirements are independent of what launches it.
- **DECISION:** A Network Extension–based `TrafficProvider` is still not achievable as a pure Rust/Tauri component — `NetworkExtension.framework` entitlements require a Swift/ObjC system-extension target that subclasses Apple's own framework classes; that requirement doesn't go away just because the host app is now native. What changes under `DECISIONS.md` ADR-013 is that this extension target can be embedded inside this app's own signed `.app` bundle using Apple's normal system-extension tooling, rather than needing an entirely separate distribution mechanism the way it would have under the FastAPI-era stack. This is not a permanent dead end for the project, but it remains a real, separate piece of Swift/ObjC work with its own entitlement-request lead time. If deeper packet-level capture is ever needed beyond what mitmproxy's local mode offers, that embedded-extension path or accepting the mitmproxy-based approach as this project's practical ceiling are the two realistic choices. See `DECISIONS.md`.
- **ASSUMED:** Certificate pinning will still defeat this approach on some target processes exactly as it would for any MITM-based approach, regardless of stack — this isn't a platform-permission problem, it's inherent to how the target app is written, and is a legitimate stopping point per the original learning path this project is based on. **Switching stacks does not change this risk at all** — it's identical to what ADR-009 already documented.

## Running the app itself

- **DECISION:** This ships as a single native, code-signed, notarized `.app`, built via `tauri build` — a real distribution path this project didn't have under the FastAPI-era stack (`DECISIONS.md` ADR-013), and closer to what the original Swift/SwiftUI plan (ADR-008) would have provided. Mac App Store distribution remains a separate, explicit future decision — it requires opting into App Sandbox entitlements, which would need re-verifying every assumption above about unsandboxed process/socket visibility; a signed-but-not-sandboxed direct download is the default target for this project, not App Store review.
- **DECISION:** Because there's no App Sandbox constraining this build, the OS-level privilege boundary around process/socket enumeration (same-user vs. other-users') is the thing that matters most for what Phase 0.1 can see without elevation — see the assumptions above.
- **DECISION:** For the "other users' processes" and any other privilege-elevation need, prefer macOS's Service Management framework (`SMAppService`, or the older `SMJobBless`) to install a small, signed, privileged helper tool with a real authorization prompt, over asking the user to launch the whole app with `sudo`. This is a genuine improvement available to a signed native app that a bare interpreted script never had a clean equivalent for. Not required for Phase 0.1 (same-user visibility needs no elevation) — worth designing once cross-user visibility is actually prioritized.

## First technical spike (still applies, framing unchanged by the stack pivot)

Confirm exactly what an ordinary, unprivileged process can read about other processes' sockets on this machine without elevated privileges, and what the underlying system calls refuse. This determines whether Phase 0.1 is trivial or the project's first real blocker — same spike as originally planned, now scoped to Rust's system-call boundary (`sysinfo`/`netstat2`/`libproc`) instead of Python's.
